# CS2 赛后采访全自动翻译流水线 — 设计文档

日期：2026-10-29
状态：第一至四阶段已实现

## 1. 目标

把现有 Electron 桌面应用（手动输入 YouTube 链接 → 转录 → 翻译）改造成一个**本地常驻服务**：

1. 拉取 HLTV 未来 5 天的比赛列表，人工勾选需要翻译的比赛（接单制，不做自动筛选）。
2. 预约时自动抓取比赛背景信息（队伍、阵容、选手、近期战绩、图池、相关新闻）。
3. 比赛进行中按比分自适应轮询（bo3.gg，失败时用 HLTV），接近结束时开始录制官方直播流的音频。
4. 边录边转录，自动定位赛后采访片段，采访结束后截取。
5. LLM 结合背景信息与术语表，产出中文翻译润色初稿。
6. 通过飞书通知人工（比赛结束、采访截取完成、初稿就绪），初稿以 Word 文件发送，人工精校得到终稿。

核心诉求是**即时性**：比赛结束后尽快出稿，因此只使用直播流，不依赖赛后上传的采访视频。

非目标：安全性、多用户、云端部署、自动筛选比赛。

## 2. 总体架构

```
┌──────────────────────── 本地服务 (FastAPI, 单进程) ────────────────────────┐
│                                                                           │
│  Web UI (React 静态资源)  ←→  REST API  ←→  Task 状态机 (SQLite 持久化)        │
│                                                │                          │
│        ┌───────────────┬───────────────┬───────┴───────┬──────────────┐   │
│        ▼               ▼               ▼               ▼              ▼   │
│   HLTV 浏览器层     比赛监视器        录音器          转录/切片        LLM 写稿  │
│   (Playwright)    (自适应轮询)   (streamlink+ffmpeg)  (faster-whisper)  (两段式) │
│        │                                                              │   │
│        └──── 实体缓存 / 术语表 (SQLite) ─────────────────────────────────┘   │
│                                                                           │
│  飞书适配器 (lark-oapi, 长连接) ── 群通知 / 交互卡片 / 文件发送                     │
└───────────────────────────────────────────────────────────────────────────┘
```

- **进程模型**：一个 Python 进程，FastAPI + APScheduler（AsyncIOScheduler）。CPU/GPU 密集的转录放线程池；录音是 ffmpeg/streamlink 子进程。
- **去掉 Electron**：前端保留 React + Vite，构建产物由 FastAPI 以静态文件托管，浏览器访问 `http://localhost:8000`。
- **存储**：SQLite 存元数据；音频、转录、稿件等大文件存 `data/tasks/<task_id>/` 目录。

## 3. 任务状态机

每个预约的比赛对应一个 Task。任何状态都允许人工**重试 / 跳过 / 注入**（上传音频、填写直播 URL、手动标注采访起止、直接粘贴转录文本），这是"人工兜底"在工程上的落点。

```
RESERVED ──(开赛前)──▶ WATCHING ──(决胜图接近结束)──▶ RECORDING
                                                        │
          ┌─────────────────────────────────────────────┘
          ▼
   (比赛结束 → 飞书通知)  ──▶  INTERVIEW_DETECTING ──(采访截取完成)──▶ QUEUED ──▶ PROCESSING ──▶ REVIEW ──▶ DONE
                                     │ 超时/未发现                                          (发 Word)   (人工确认终稿)
                                     ▼
                                NO_INTERVIEW（仍可人工标注起止或上传音频）
任意状态 ──▶ FAILED（记录原因，可从失败步骤重试）
任意状态 ──▶ CANCELLED
```

手动创建的任务（上传音频或填写视频链接）从 DRAFT 直接进入 PROCESSING。PROCESSING 内部按阶段（stage）串行执行：
`context`（背景信息）→ `ingest`（获取音频）→ `transcribe`（转写）→ `clean`（英文清洗）→ `write`（中文成稿 + 名词规范化）→ `export`（Word）→ `deliver`（飞书发送）。
每个阶段只读写任务目录里的文件，因此可以从任意阶段重跑，也可以只跑某一段（如只重新抓取背景信息）。

`task_events` 表记录每次状态迁移和日志，Web UI 与飞书卡片均以此为数据源。

## 4. 模块设计

### 4.1 HLTV 浏览器层（解决 Cloudflare）——已实现

旧版用 curl-cffi 伪造 TLS 指纹，挂代理时高概率被 Cloudflare 拦截。

**决定：用 Playwright 驱动真实 Chrome，不用 LLM Agent。**
Cloudflare 拦截看的是浏览器指纹和行为，不是"会不会看网页"。LLM Agent 解决不了指纹问题，还会带来延迟、费用和不确定性。确定性的浏览器自动化加人工兜底就够了。

实现（`backend/sources/browser.py`）：
- `playwright` + 本机 Chrome（`channel="chrome"`），默认**有头模式**，**持久化用户目录**（`data/browser-profile/`），通过代理启动。`cf_clearance` 等 cookie 持久保存。
- 所有浏览器操作在一个专用线程中串行执行，两次访问至少间隔 3 秒加随机抖动。空闲 10 分钟自动关闭浏览器。
- 遇到验证页先自动等待 45 秒；仍未通过就发飞书通知"HLTV 需要人工验证"，在弹出的 Chrome 窗口里点一下即可，最多再等 5 分钟。
- 以"拿到了真正的 HLTV 页面"（`<html>` 上有 `data-client-country-iso`）作为通过的标准，不靠识别验证页：验证页的文字随浏览器语言变化（中文系统下标题是"请稍候…"）。

**验证反复弹出的原因（实测 2026-10-30）**：启动参数里固定了视口大小（1280×860）和 `locale="en-US"`。页面尺寸、语言和真实窗口对不上，Cloudflare 的验证就一直过不去，人工点了也会转一会儿再弹出来。去掉这两项后，同一个用户目录、同样的代理，约 20 秒自动通过，之后的页面 1～6 秒加载完。对比过 patchright（号称修补了自动化特征的 Playwright 分支），反而一直过不去，没有采用。
- 解析是纯函数（`backend/sources/hltv_parse.py`），测试样本裁剪自真实页面（`tests/fixtures/hltv/`）。HLTV 改版时先看这里。

实测（2026-10）：`/matches`、比赛页、战队页、搜索页都能直接通过；`/stats/...` 统计页的验证更严，需要人工点击。因此**图池数据改从战队页的「Map win statistics past 3 months」读取**，不访问统计页。

对外接口（`HLTVClient`，带内存缓存）：
- `list_matches()`：比赛列表（id、时间、星级、双方、赛事、阶段、BO 数、是否进行中）
- `get_match(id)`：比赛页（当时的阵容含真名/国籍/替补、排名、BP、各图比分、双方近期战绩、交手记录、直播源）
- `get_team(id)`：战队页（教练、当前阵容、排名、近 3 个月图池、最近 5 场、相关新闻）
- `search_team(name)`：按队名找战队 ID（手动任务未关联比赛时使用）

比赛监视的比分另有 bo3.gg 数据源，HLTV 不可用时自动切换，见 4.4。预约、阵容仍以 HLTV 为准（选手名写法要和 HLTV 一致）。

### 4.2 比赛列表与预约——已实现

- Web UI「比赛」页显示 HLTV 未来 5 天的比赛，按日期分组，可按队名/赛事搜索、按星级筛选。列表缓存 10 分钟，可手动刷新。
- 点「预约」创建 Task（状态 RESERVED，标题自动生成），立即抓取背景信息（只跑 `context` 阶段，完成后回到 RESERVED）。
- 手动任务也可以填 HLTV 比赛链接，按这场比赛抓取背景信息。
- 第三、四阶段完成前，预约的任务在比赛结束后由人工上传采访音频，上传后自动走完后处理。

### 4.3 背景信息抓取与知识库——已实现

以**比赛页**为主，**战队页**补充：

| 内容 | 来源 | 用途 |
|---|---|---|
| 比赛当时的阵容、真名、国籍、替补 | 比赛页 | ASR 提示词、LLM 名单、名词规范化 |
| 赛事、阶段、BO、时间、BP、各图比分、交手记录 | 比赛页 | 稿件背景 |
| 双方近期战绩（含对手队名） | 比赛页 | 稿件背景；对手队名也加入规范名单 |
| 教练（含全名） | 战队页 | 规范名单 |
| 图池（近 3 个月胜率、选图/禁图率） | 战队页 | 稿件背景 |
| 相关新闻标题（近 14 天） | 战队页 | 稿件背景 |

战队页是"当前"数据：只有比赛发生在最近 30 天内才使用；更早的比赛只用比赛页（阵容以比赛当时为准），并在日志中提示。

每个字段独立抓取、独立失败。失败字段在 UI 和飞书卡片中标红，可人工补填，不阻塞主流程。

**知识库**（初期不做 RAG）：
- `glossary` 表：CS 术语固定译法、选手和队伍的中文社区惯用称呼，Web UI 可编辑。
- `style_examples`：2～3 篇历史终稿，作为 few-shot 风格示例。
- 每篇终稿与初稿的 diff 会存档，用于后续人工迭代术语表和 prompt。

### 4.4 比赛监视器（自适应轮询）——已实现

实现：`backend/pipeline/watcher.py`。开赛前 15 分钟（`pre_match_minutes`）进入 WATCHING；预约时队伍还是 TBD 的，此时重新抓取阵容。

**比分数据源可替换**（`backend/pipeline/match_sources.py`）：按设置里的顺序依次尝试（默认 `["bo3", "hltv"]`），前一个失败自动用下一个。每个数据源返回同一种结构（地图列表和胜负、比赛状态、实时比分、直播源）。

| 数据源 | 方式 | 实测（2026-10） |
|---|---|---|
| bo3.gg | 公开 JSON 接口 `api.bo3.gg/api/v1`，httpx 直接请求，不需要 key、不需要浏览器（bo3.gg 网站本身有 Cloudflare，接口没有） | 每张图的 upcoming / current / finished 和胜方、比分；普通比赛**没有回合级实时比分**（`live_coverage=false`）。单场 `with=games,streams` 带直播源，`official=true` 是赛事方的流（含各语言官方二路），未开赛时通常是空的。接口无文档，不支持按日期过滤，带 `with=tournament` 会 500 |
| HLTV | 浏览器标签页里的比赛页（4.1） | 有实时比分板；偶尔需要过 Cloudflare 验证 |

- bo3.gg 上没有 HLTV 的比赛 ID，按队名 + 开赛时间（12 小时以内）匹配，结果存进 live.json；队名先规范化（小写、去掉 team / esports / gaming / cs2 等词）再比较，能对上 `Team Falcons`、`mouz cs2` 这类写法。匹配不上时可在任务页手动粘贴 bo3.gg 比赛链接。
- 数据源没有回合比分时（bo3.gg 普通比赛）：决胜图开打后改从 **HLTV 比分板补回合比分**，照常按领先方回合数判断；HLTV 也读不到时，**决胜图开打 `no_score_record_minutes`（默认 15）分钟后录制**。开打时间取 bo3.gg 每张图的 `begin_at`，没有就用第一次看到这张图在打的时刻。
  - 起因：实测 BO3 0:1 时第二张图刚开打就开录。0:1 时第二张图确实可能是最后一张（领先方再赢就结束），不能跳过，但一张图最快也要 20 分钟以上，刚开打就录只会让录音和 LLM 定位白跑。
- 直播源选择：频道名和赛事名里的主办方词对得上的优先（DFRAG → DFragTV、PGL → twitch.tv/pgl），其次才看 HLTV 的 "Other" 标记——HLTV 也会把 "Other" 标在个人二路主播上。
- bo3.gg 的图数以大比分（`team1_score` / `team2_score`）为准：实测一张图打完后大比分先变，这张图的状态半分钟后才变成 finished，胜方和比分还要更晚才填上。
- 所有数据源都失败：记一条日志；连续 5 分钟发飞书提醒；开赛后连续 10 分钟，保险起见直接开始录制（采访定位在录制期间一直在跑，不依赖"比赛结束"信号）。任务页有「比赛已结束」按钮，可以人工确认。
- 录制中就截取了采访（比赛结束信号还没到）的任务，继续跟踪比分到比赛结束，用来更新最终比分。

为什么不用其他数据源：HLTV 没有官方 API，服务条款禁止抓取；PandaScore 免费版有每小时 1000 次的额度但要注册 token，实时推送要付费；Liquipedia 的 API 有严格的频率限制，适合查历史阵容而不是轮询比分；GRID 的实时数据只给商业合作方。

核心是判断**决胜图**：任一方再赢下当前这张图即可赢下整场（BO1 的唯一一张图；BO3 中某方已赢 1 张图；BO5 中某方已赢 2 张图）。

轮询间隔（设置页可改）：

| 状态 | 间隔 |
|---|---|
| 未开赛 / 非决胜图 / 决胜图还没开始 | 10 分钟 |
| 决胜图，领先方回合数 < 8 | 10 分钟 |
| 决胜图，领先方回合数 8～10 | 5 分钟 |
| 决胜图，领先方回合数 ≥ 11，或进入加时 | 2 分钟 |
| 已开始录制后 | 1 分钟（只为尽快确认结束） |

**读比分不刷新页面**（实测 2026-10）：比赛页的实时比分板（`.scoreboard`，scorebot 通过 websocket 推送）在后台标签页里也会持续更新。因此每场比赛在 Chrome 里单独开一个标签页并一直保持打开，每次检查只读 DOM，不产生请求。地图栏的各图胜负和比赛状态（LIVE / Match over）不会实时更新，只在以下情况刷新页面：距上次加载超过 10 分钟、未开赛、比分板消失（换图间隙或已结束）、比分板的地图和地图栏里进行中的地图不一致（换图了）、某方达到 13 分且领先（这张图可能刚打完）。距上次加载不到 90 秒时绝不刷新——实测连续两次加载会触发 Cloudflare 验证。

以上是 HLTV 数据源的做法。比分板按 CT / T 两边显示，按队名对应到 team1 / team2。

- **开始录制**：决胜图上**赛点方**（再赢一张就拿下系列赛的一方）回合数 ≥ 10（`record_at`）或进入加时。实测 HLTV 比分比直播画面快好几分钟，余量充足。
  - 只看赛点方：BO3 1:0 时第二张图如果是落后方领先，打完是 1:1、还要打第三张；以前按两边较高分判断，会提前一整张图开录。BO5 2:1 同理。1:1、2:2 时两边都是赛点。
  - **暂停录制**：自动开录后有图打完、系列赛却没结束（没有回合比分、按开打时长开录的那张图被另一方拿下），停止录制、回到监视，等下一张决胜图；人工开录的不管。
- **比赛结束**：HLTV 显示 Match over，**或者某方已经拿够图数**（实测对手投降时 HLTV 把那张图记为 8:4 获胜，但状态仍停在 LIVE）。发飞书通知，背景信息里的比赛结果更新为最终比分，状态进入 INTERVIEW_DETECTING，录音继续。如果这时还没在录（例如开赛前服务没开），立即开始录。
- 每个关键节点发飞书通知：比赛开始、开始录制（附比分和直播源）、比赛结束、检测到采访、采访已截取、未发现采访、录制异常，都附带任务详情链接。

### 4.5 录音器——已实现

实现：`backend/pipeline/recorder.py`。

- **选直播源**：候选来自三处，按 URL 去重：当前数据源给的、预约时 HLTV 比赛页上的、同一赛事以前的任务实际用过的。HLTV 列表里官方流的国家标记是 "Other"（地球图标），其余基本是各国二路解说；bo3.gg 的官方英文流也记为 "Other"。优先 Other，同为官方时 HLTV > 同赛事用过的 > bo3.gg（实测 bo3.gg 的 PGL 比赛只列了法语、乌克兰语官方二路，没有主直播），再按 Twitch > YouTube > Kick、来源、观看人数；指向具体某场直播的 YouTube 链接（`watch?v=`、`youtu.be/`、`/live/<id>`）排在频道链接之后，也不作为“同赛事用过的”记下来——实测 Nemiga vs Vitality 预约时 HLTV 给的 PGL YouTube 链接，到第二天开录时已是前一天的回放，录到的是昨天的比赛。实测 PGL 选到 twitch.tv/pgl，StarLadder 选到 kick.com/starladder。任务页可以从列表里换一个，或直接填直播链接，录制中切换时间轴不断。
- `streamlink`（Twitch 取 `audio_only`、加 `--twitch-disable-ads`；YouTube、Kick 取最低画质）输出到 stdout，`ffmpeg` 转成 16kHz 单声道，按 **30 秒分段**（`chunk_seconds`）写入 `chunks/c_YYYYmmdd_HHMMSS.wav`。文件名带开始时刻，断流重连、服务重启后时间轴仍然连续可算。
- 断流自动重连（3 / 5 / 10 / 20 / 30 秒退避），连续失败 3 次发飞书通知，但不放弃，直到被停止。
- **回放检测**：连上 45 秒后，这次连接录到的音频比经过的时间多 40 秒以上（下载比实时快），就判定不是直播：停掉这个源，把它录到的分段挪到 `rejected/`、从滚动转写里删掉，记入 `bad_streams` 不再选，自动换下一个候选并发飞书通知；没有可换的就停止录制，等人工填直播链接。
- 停止条件：采访截取完成；比赛结束后 30 分钟（`max_post_match_minutes`）仍未发现采访；一直收不到比赛结束信号时录满 6 小时；人工点「本场无采访」或取消。
- 服务重启时，处于录制 / 采访监听状态的任务自动继续录（同一个分段目录）。

### 4.6 滚动转录与采访定位——已实现

实现：`backend/pipeline/live.py`。为了即时性，**边录边转**：

1. 每写完一个分段，就用 faster-whisper 转写（beam 1，`initial_prompt` 注入双方阵容），结果追加到 `live_transcript.jsonl`，时间为"相对录制开始的秒数"。3060 Ti 上 large-v3 转一个 60 秒分段约 3～4 秒。直播转写和后处理转写共用一把 GPU 锁，不同时占显存。
2. **录制期间**（不等比赛结束），每有新的转写、且距上次判断超过 30 秒（`detect_interval`），就把最近 15 分钟的转写（已发现采访开始时，从开始前 1 分钟起）交给 LLM，输出 `{started, start, ended, end, interviewee, confidence, note}`。还没收到比赛结束信号时，提示词里说明"比赛可能还在进行，比赛解说不是采访"。LLM 用设置里「直播采访定位」那一步的模型（选响应快的），没选就用「英文清洗」的。LLM 给的结束时间是最后一句的开头，换算成这句话的结束时间；"录音开始时采访已在进行"时沿用之前的起点或取窗口开头。
3. **结束要确认一次**：第一次判定"已结束"只记下来，下一次判断（看到了更多内容）给出的结束时间和它相差 45 秒以内才截取。实测有一次 LLM 把采访中途的"明天的对手是谁"当成了结束（判在 01:00，实际 03:00），直接截取会停掉录音、丢掉后半段采访。
4. 截取：按起止各加 10 秒余量（`padding_seconds`）从分段里截取拼接成 `interview.wav`（缺失部分补静音），停止录音，从「获取音频」开始跑后处理流水线（转写 + 说话人分离 → 两段 LLM → Word → 飞书）。
5. 之前判定采访开始、后一次判断说没有采访，就撤回起点（实测一次判断把赛间播放的预录选手专访当成了采访）。采访开始后 10 分钟（`max_interview_minutes`）仍未判定结束，直接截到当前位置；比赛结束 10 分钟（`alert_no_interview_minutes`）还没发现采访发飞书提醒；LLM 连续失败 3 次发飞书提醒。
6. 实测（PGL Masters Bucharest，FURIA 赛后采访 YEKINDAR）：录到第 2.5 分钟时判定"已开始、未结束"，第 5 分钟和第 11 分钟都判定在 02:43 结束、转回解说台，和实际一致。

### 4.6.0 画面：镜头时间轴

借鉴 claude-real-video 这类“让 LLM 看视频”的工具（抽帧 + 带时间戳的帧清单 + 3×3 拼图按顺序读）：

- 录制改拉最低画质视频（144p/160p，带宽可忽略），ffmpeg 同一路输入另出一路：每 `frame_interval`（默认 5）秒存一帧 320 宽的 JPEG 到 `frames/f_YYYYmmdd_HHMMSS.jpg`。
- 每凑满 9 帧拼成一张 3×3 图，每格标序号和录音时间，交给采访定位那一步的模型（d1 / deepseek，支持图片）一次给 9 帧打标签：interview（主持人拿话筒和选手）/ desk（解说台）/ game（比赛画面、数据）/ other（广告、预录专访等），追加到 `shots.jsonl`。约 830 token、几秒一次。
- 连续的采访镜头合成一段（中间插 15 秒以内的回放不算断开，短于 20 秒的忽略）；镜头切走并持续 30 秒以上才算这段结束。
- 和采访定位的关系：转写仍决定“是不是现场赛后采访、谁接受采访”；镜头段写进定位提示词。和转写起点对得上的镜头段**已切走就直接截取**（起点取两者较早，终点取镜头切走的那一帧），不用等转写那边两次确认；镜头还在采访时，转写说“已结束”也不截。没有对得上的镜头段（比如在解说台上采访）时照旧按转写判断。
- 实测 Nemiga vs Vitality 回放：镜头 12:05–15:30，转写 11:30 起，截取 11:30–15:30，采访结束后约 1 分钟截取（只看转写时约 2 分钟，而且之前会在换人提问时被截断）。

### 4.6.1 时效：采访结束后多久出初稿

目标：采访结束后 5 分钟内开始处理，15 分钟内出清洗过的初稿，最晚不超过 20 分钟。

实测各段用时（2026-10-30，3060 Ti，d1 / gemini-3.8-flash）：

| 环节 | 用时 | 说明 |
|---|---|---|
| 采访结束 → 截取 | 约 1.8 分钟 | 用 PGL 真实录音回放：30 秒分段、30 秒判断一次、结束确认一次。采访在录音 03:00 结束，04:49 截取。其中 LLM 单次响应 8～58 秒，波动最大 |
| 截取 → 初稿 | 约 1 分钟（110 秒采访） | 转写 4 秒、说话人分离 37 秒、英文清洗 9 秒、中文成稿 15 秒、Word 不到 1 秒。5 分钟的采访估计 2～3 分钟 |
| 合计 | 约 3～5 分钟 | 远低于 15 分钟 |

保证措施：
- 录制期间就判断采访，不等比分数据源报告比赛结束（数据源慢了或挂了都不耽误）。
- 直播任务在执行器里单独一条车道，不会排在上传的长视频后面。
- 初稿完成时记录"采访结束后 X 分钟出初稿"（日志和飞书消息里都有）；采访结束 15 分钟（`draft_deadline_minutes`）还没出初稿就发飞书提醒。处理失败另有失败通知。
- 主要风险是 LLM 响应慢或失败：可以给「直播采访定位」单独选一个快的模型；连续失败会提醒，任务页随时可以手动标注起止。

**人工兜底**（任务页「直播」）：实时比分和各图状态、换直播源、立即开始录制；滚动转写里悬停一行即可设为起点 / 终点，试听确认后「截取并开始处理」；「本场无采访」；取消预约。

飞书交互卡片（在飞书里直接点按钮）暂未实现：需要在飞书开放平台开通长连接事件订阅，Web UI 已经覆盖同样的操作，确有需要时再加。

### 4.7 LLM 写稿（两段式）

复用 `llm_service.py` 的多供应商调用层，把 prompt 拆成两步：

1. **英文清洗**：输入转录、说话人、选手名单、术语表；输出规范化的问答稿，修正拼错的选手名和术语、去掉口头禅、标注听不清的部分 `[?]`。
2. **中文成稿**：输入清洗后的问答稿、比赛背景（比分、图池、近期战绩、新闻）、风格示例、交稿要求；输出中文新闻稿（标题 + 导语 + 问答正文）。

两步的中间结果都保存，人工可以从任一步重新生成。

### 4.8 飞书适配器

使用飞书**自建应用** + `lark-oapi` Python SDK，事件和卡片回调走**长连接模式**，本地服务不需要公网 IP。

通知（发到指定群）：

| 时机 | 内容 | 交互 |
|---|---|---|
| 预约成功 | 比赛信息、背景信息抓取结果（失败项标红） | 打开 Web UI |
| 开始录制 | 比分、直播源 | 停止 / 换流 |
| **比赛结束** | 最终比分，提醒人工关注 | 标记无采访 / 手动停止 |
| 检测到采访开始 / 结束 | 起止时间、前几句转录 | 确认 / 手动修正起止 |
| 初稿就绪 | Word 文件 + 待核对名词列表 | 标记完成 |
| 异常 | 失败步骤、原因 | 重试 / 跳过 |
| HLTV 需人工验证 | — | — |

初稿以 Word 文件（见 4.9）的形式通过飞书消息直接发送到群聊或个人，人工下载后在 Word 里精校。终稿可以在 Web UI 上传回来存档，并和初稿做 diff（可选）。

### 4.9 Word 稿件格式

用 `python-docx` 生成，规则如下：

- 正文为问答体。主持人提问为一个段落：`Q：<问题>`，**整段加粗**。
- 选手回答为一个段落：`A：<回答>`，不加粗。
- 全文字号统一为小四（12pt），字体使用 Word 默认字体，除 Q 段落外任何地方都不加粗。
- 如果 LLM 输出了标题或导语，作为普通段落放在问答之前，同样不加粗。
- 文件名：`<日期>_<队伍1>_vs_<队伍2>_<选手>.docx`。

LLM 第二步输出约定为纯文本行（`Q：...` / `A：...` / 普通段落），由程序转换成 docx，不让 LLM 直接控制格式。

### 4.10 专有名词规范化（选手名、战队名与 HLTV 一致）

这是硬性要求，靠 prompt 不够，用"词典 + 确定性替换 + 校验"三层保证：

1. **规范词典**：预约时从 HLTV 抓取的双方阵容、教练、队名，以 HLTV 页面上的写法作为规范形式（如 `m0NESY`、`ZywOo`、`Natus Vincere`）。每个规范名自动生成一个"匹配键"：转小写，再把 leet 字符归一（`0→o`、`1→i`、`3→e`、`4→a`、`5→s`、`7→t`、`$→s`），去掉空格和符号。例如 `m0NESY`、`monesy`、`Mo Nesy` 的匹配键都是 `monesy`。术语表中可人工添加别名（如 `NAVI → Natus Vincere`、中文音译 → 规范名）。
2. **三处使用**：
   - ASR：规范名写入 Whisper `initial_prompt`。
   - LLM：两步 prompt 都附带规范名单，并要求严格使用。
   - 后处理：对 LLM 每一步的输出做确定性替换。扫描所有拉丁字母/数字组成的词（含相邻的 1～3 个词组合），匹配键命中词典就替换为规范形式。
3. **校验**：替换后再扫一遍，对编辑距离接近规范名但未命中的词（可能是识别错误的变体）在 Web UI 和飞书通知中列出，提醒人工核对。

### 4.11 Web UI（调试与设置）

只做必要页面：
- **比赛列表**：未来 5 天比赛，一键预约。
- **任务列表 / 详情**：状态时间线、日志、实时比分、录音分段、滚动转录、采访起止标注、背景信息（可编辑）、各步重试和注入入口、稿件预览。
- **设置**：代理、LLM 供应商和模型、Whisper 模型、飞书凭据和群 ID、轮询阈值、术语表、风格示例。

## 7. 分阶段实施

按"先打通后处理，再做前置自动化"的顺序推进，每个阶段都能独立使用：

1. ✅ **骨架 + 后处理链路**：新目录结构、SQLite、状态机、FastAPI 托管前端；手动上传音频或输入 URL → 转录 → 两段式 LLM → 名词规范化 → Word → 飞书发送。可以用历史采访录像离线测试。
2. ✅ **HLTV 浏览器层 + 比赛列表 + 预约 + 背景信息抓取**，以及术语表（预置常见战队简称）。
3. ✅ **比赛监视器 + 飞书通知**（比赛开始 / 开始录制 / 比赛结束 / 采访 / 异常）。飞书交互卡片暂缓，操作都在 Web UI。
4. ✅ **直播录音 + 滚动转录 + 采访定位**：已用真实比赛跑通，采访定位的准确率还要在更多比赛里观察、调提示词。
5. 打磨：UI 细节、diff 存档、prompt 迭代。

## 8. 已确认事项（2026-10-29）

1. **硬件**：测试机为 RTX 3060 Ti 8GB，跑通后迁移到 RTX 5070。faster-whisper 使用 `float16`/`int8_float16`：滚动转录默认 `large-v3-turbo`，采访片段精转默认 `large-v3`。模型、计算精度可在设置中切换。Whisper 与 pyannote 串行占用 GPU，避免 8GB 显存溢出。
2. **LLM**：不设默认供应商。设置页提供"自定义供应商"列表：每项含名称、协议类型（OpenAI 兼容 / Anthropic 兼容）、Base URL、API Key、模型名，可添加多个；两段式写稿的每一步可以分别指定使用哪个供应商和模型。
3. **代理**：HLTV、直播拉流、LLM 请求统一走同一个代理，默认 `http://127.0.0.1:7897`，可在设置中修改或关闭。
4. **飞书**：使用自建应用，通知目标可配置为群聊（chat_id）或个人（open_id）。
5. **稿件格式**：产出 Word 文档（.docx），见 4.9。
6. **专有名词**：选手名、战队名必须与 HLTV 完全一致（大小写、数字都一样，如 `m0NESY`），见 4.10。
